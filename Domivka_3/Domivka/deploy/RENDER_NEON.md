# Domivka: Render Free + Neon

Бот і Mini App працюють в одному Python web service. Комп'ютер власника після запуску не потрібний. Telegram надсилає оновлення через HTTPS webhook, тому polling на засинаючому тарифі не використовується.

## Межі безкоштовного тарифу

Render Free засинає після періоду без HTTP-запитів; перше відкриття або команда може чекати пробудження. Це не always-on тариф і не гарантія миттєвої відповіді цілодобово. Фонові нагадування виконуються лише коли процес працює; під час сну планувальник не запускається. Telegram повторює невдалі доставки webhook, але не зберігає оновлення безстроково. Для гарантованих своєчасних нагадувань потрібний постійний compute або окремий підтримуваний планувальник.

SQLite на Render Free НЕ використовується: локальні файли зникають після перезапуску/деплою. DATABASE_URL має вести до постійної зовнішньої PostgreSQL бази. Не обирайте тимчасову Render Free Postgres базу як постійне сховище. Фото оголошень залишаються Telegram file_id, а не локальними файлами.

## Створення

1. Створіть Neon Free проект domivka у Frankfurt, лише Postgres. Збережіть звичайну PostgreSQL connection string через Connect, вимкнувши pooling. Початкова ініціалізація схеми виконується тим самим процесом, тому потрібне пряме з'єднання з sslmode=require. У поточній конфігурації один екземпляр сервісу й невелика фіксована кількість з'єднань; масштабування потребує окремої міграції та пулу.
2. У Render виберіть репозиторій Domivka3, гілку codex/domivka-marketplace, Python, root directory Domivka_3/Domivka, регіон Frankfurt, compute Free.
3. Build command: pip install -r bot/requirements.txt
4. Start command: python -u bot/bot.py
5. Health check: /api/identity. Auto deploy: After CI Checks Pass.
6. Додайте змінні нижче через Environment Variables. Вони не повинні потрапляти до git. render.yaml у корені репозиторію містить такий самий шаблон для альтернативного Blueprint створення; не створюйте другий сервіс поруч із уже налаштованим вручну.

| Змінна | Значення |
| --- | --- |
| BOT_TOKEN | Секрет BotFather для цього бота |
| DATABASE_URL | Секретне пряме Neon PostgreSQL з'єднання з TLS |
| OWNER_ID | Telegram ID незмінного власника |
| ADMIN_IDS | Telegram ID адміністраторів через кому; спочатку ID власника |
| EXPECTED_BOT_USERNAME | Рекомендовано: username цього бота без @ |
| WEBHOOK_SECRET | Випадковий постійний секрет; Generate у Render |
| DEPLOYMENT_MODE | production |
| BOT_MODE | webhook |
| TUNNEL | off |
| WEBAPP | on |
| WEBAPP_HOST | 0.0.0.0 |
| REQUIRE_APPROVAL | 1 |
| PAYMENT_MODE | direct |
| PYTHON_VERSION | 3.12.12 |
| PYTHONUNBUFFERED | 1 |

Render сам задає PORT і RENDER_EXTERNAL_URL. WEBAPP_URL можна не задавати: використовується адреса саме цього сервісу. Для власного домену задайте окремий HTTPS origin у WEBAPP_URL після налаштування DNS/TLS. Перевірка /api/identity з bot_id захищає від випадкового підключення Mini App іншого бота.

## Дані наявного локального бота

Нова база порожня. Користувачі, оголошення, замовлення та налаштування з локального data/domivka.db самі не переносяться. Перед перенесенням збережіть копію робочої бази, зупиніть локального бота і виконайте перевірений імпорт у тестову гілку Neon. Не очищуйте робочу SQLite базу та не перезаписуйте заповнену PostgreSQL базу. Для перемикання користувачів із наявними оголошеннями імпорт є окремим обов'язковим кроком.

## Перевірка після деплою

- Переконатися, що GitHub checks і Render deploy завершилися успішно.
- Перевірити /api/identity: service=domivka, очікувані bot_id та username; /api/version показує версію.
- Надіслати /start, /market, /rent, /account потрібному боту. Перевірити відкриття його власного Mini App.
- Зупинити локальний Start Bot для цього самого токена: локальний polling видаляє webhook і конфліктує з сервером. Другий бот з іншим токеном може працювати окремо.
- Перевірити збереження тестового оголошення після рестарту Render.
- Перевірити секрет webhook: запит без правильного заголовка відхиляється. Невдалий обробник повертає 503, щоб Telegram повторив доставку; успішно завершені update_id зберігаються. Збій між бізнес-записом і receipt може повторити дію, тому критичні оплати мають власну ідемпотентність.

SQLite щоденні локальні копії вимкнено у PostgreSQL режимі. Резервування Neon залежить від доступного плану та retention; для довгострокових копій налаштуйте контрольований pg_dump окремо. Не називайте ephemeral-файл на Render резервною копією PostgreSQL.

Ключ Нової пошти та доступи платіжних провайдерів налаштовуються окремо в секретах сервісу. Сам деплой не активує договори доставки, оплату або автоматичні ТТН без дозволів оператора.
